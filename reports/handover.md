# 软切换：新通道先建立，旧包发完并排空

2026-09-27。继多端口/padding 初版之后，将“先断旧连接再握手”改为后台握手与短暂双接收。端口配置、v2 padding 格式、1500 MTU、UDP 1200 上限和 80 Mbps pacer 保持不变。

## 分界与实现

1. 定时器到期，在后台连接下一个端口；旧通道持续处理业务。新端口握手失败时保留健康旧通道，等待 2 秒尝试下一个候选；多端口时跳过正在使用的端口。
2. 新 DTLS 会话双向身份认证完成后，停止旧发送器领取新的 IP 包。它正在处理的那个 IP 包会将所有分片发完，然后新发送器接管完整包队列。
3. 不清空交接时尚未发送的完整 IP 包。只有实际断线后重连，才清理旧队列；正常交接没有该丢弃步骤。
4. 旧接收器保留 1 秒，继续解密、重组旧通道迟到的分片；新接收器同时工作，完整 IP 包汇入同一个 TUN。旧会话到期后关闭并释放资源。
5. 每个 IP 包的分片始终在同一个 DTLS 会话里传递，不跨会话拼接，不额外双发。新旧会话独立密钥、记录序号和重组状态，避免同名包 ID 混用。新增并发重组表的累计资源计数，旧表退出不会清零新表的状态。
6. 最终版本所有监听、握手和业务会话共用一个进程级 pacer，避免交接时每条通道各自获得完整 80 Mbps 额度。

这里“旧包”指已经开始在旧会话发送的包；尚未分配给发送器的完整 IP 包可由新通道发送。并不是把旧、新密文放进一个解密器；统一的是解密重组后的 L3 交付。

这属于 make-before-break：到切换时刻后台建连，旧连接一直保留到新连接就绪；不是提前数分钟建立闲置备用会话。客户端和服务端的交接时刻不必完全同步，双接收窗口承接短暂差异。

## 验证与对比

单元测试明确在第一片发出时请求停止旧发送器，验证第二片仍发送、下一个完整包保留队列；随后给已停发会话送入迟到的两片，仍成功重组并交付。另验证新旧重组表共存时，释放旧表不破坏新表计数。`go test -race ./...`、`go vet ./...` 通过。

隔离网络复用初版测试条件：每 5 秒切换，40 秒双向 TCP + 1 Mbps UDP + MTU 1500 ping。各一次运行，不能当作多轮统计保证：

| 指标 | 初版先断后连 | 软切换 |
|---|---:|---:|
| TCP 正向 | 59.33 Mbps | 62.38 Mbps |
| TCP 反向 | 60.69 Mbps | 60.64 Mbps |
| UDP 丢包 | 12/3397（0.353%） | 5/3397（0.147%） |
| MTU 1500 ping 丢包 | 4/400（1%） | 1/400（0.25%） |
| 封锁候选 443 时 ping 成功 | 93/175 | **175/175** |

新版故障测试在确认当前为 80 端口后封锁 443，明确测“候选端口失败、当前路径健康”；旧版故障窗口也保留原始记录，但未用同样的显式同步，所以只作行为对照。新版记录有候选握手超时，但无业务中断；恢复后可再次使用 443。混合高负载下仍有队列丢包，不能把每一个剩余丢包归因于或排除切换。

本轮隔离实验成功建连 19 次。抓包最大外层 UDP 载荷仍为 1173，无外层 IP 分片；保持随机 1–20 字节 padding。隔离实验在增加共用 pacer 之前完成；该最后调整另经单元/race 检查和公网运行验证。

原始数据：`handover-lab/`；单元及公网记录：`handover/`。初版原始数据与报告保留，没有覆盖成新版结果。

## 边界

软切换尽量减少由交接造成的损失，不是可靠 UDP：真实网络丢包、超过 1 秒的迟到片、重组超时、队列满、旧路径本身故障、握手最后报文异常等仍可能导致丢包。未加入 ARQ/FEC 或跨会话重复发送。旧接收保留与原有 1 秒重组超时都是有限窗口。

短暂共存时按会话分别限制重组资源，总计可能超过单会话 4 MiB；通常是新旧两个接收会话。所有接收会话仍采用相同 pin 认证及源 IP 限制。此功能不能证明或保证解除 ISP 的限速。

## 公网测试（每 10 秒切换）

与初版相同的长连接测试：正向 30 秒 **66.57 Mbps**（初版 60.67），反向 25 秒 **56.23 Mbps**（初版 47.29）；MTU 1500 ping **597/600**（初版 587/600）。属于不同时间的一轮对比，有公网波动，不能声称全部增益来自代码。两条 TCP 都跨越多次端口交接并完成，没有因切换被重建成新的业务连接。

CPU：北京正/反向约 34.4% / 30.3%，香港 54.4% / 49.9%（100%=一个核）；RSS 峰值约 14.4 MiB。当前运行间隔恢复 **10 分钟**，端口 80/443/23333、pacer 80 Mbps；仍没有隧道默认路由。

从测试间隔恢复 10 分钟时重启了客户端进程。首次尝试的 80 端口仍持有旧会话，等待握手超时后转到 443，总启动恢复约 12 秒；随后 MTU 1500 ping 通过。这是进程重启场景，不是正常定时软切换；当前未实现同端口并发接收新来源连接。

## 关于原先那 1 次 ICMP 丢包

混合测试缺失的是 ICMP 序号 17，约在负载开始后 1.6 秒，附近有切换，也有队列溢出。原抓包仅覆盖基础测试，没有覆盖该混合负载；15 秒汇总计数不足以将它与具体丢弃事件匹配。因此不能准确追溯这一次，更不能仅凭附近有切换就断言是切换丢包。

后续增加默认关闭的 `--trace-icmp-drops`：只记录本地因队列满或未连接而丢弃的 ICMP echo 的地址、类型、identifier 和 sequence，不记录 payload。配合混合阶段两端 TUN 的 ICMP 抓包，可将新复现的丢失序号与具体本地丢弃匹配。诊断脚本为 `scripts/icmp-diagnose-hook.sh`。

### 新诊断样本的证据

三轮各 200 次 ping，混合负载与每 5 秒切换，分别收到 200、199、199 次回复。

- 第三轮 identifier=30367、seq=10：两端抓包均看到请求，服务端看到生成的回复；服务端日志同序号明确记录 `icmp_drop reason=queue_full ... type=0 id=30367 seq=10`，客户端未收到回复。因此这一例的直接原因是服务端完整包发送队列满，发生在加密发送之前。时间 23:49:58，最近的交接是 23:49:55，下一次为 23:50:00；它不是交接瞬间直接销毁半包的证据，但不能仅此完全排除切换对负载的间接影响。
- 第二轮 identifier=30333、seq=126：请求抵达服务端并生成回复，但客户端 TUN 未看到回复，没有匹配的本地 ICMP 队列丢弃日志。可定位到回程隧道路径，不能进一步断言是 socket、分片、DTLS 还是会话交接所致；同一汇总窗口有一个重组窗口淘汰，但没有包 ID/序号关联，不能当成已证实的原因。

这两例均是新复现的样本，不能倒推旧测试第 17 次的准确原因。数据和对应关系保存在 `handover-icmp-diagnosis/diagnosis.json` 与两端 ICMP 抓包文本；pcap 原件保留在北京测试目录。默认生产配置不开启诊断日志。
