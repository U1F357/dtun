# 重组过载缓解：实现与对照实验

日期：2026-09-27。目标是缓解链路突然降速时 TUN + DTLS 的额外丢包，不引入 HY2、可靠外层或业务 TCP 代理。公网继续使用双向 80 Mbps 固定 pacer、测试 UDP 端口、TUN MTU 1500。

## 结论与边界

相同的 20 Mbps 外层瓶颈、80 Mbps pacer、100 Mbps UDP 应用输入下，接收有效吞吐从 **2.77 提升到 11.00 Mbps，约 3.97 倍**，丢包率从 **97.11% 降到 88.76%**。这是隔离环境的三轮交错对照均值，不是公网 TCP 提速倍数。

已消除该工况下重组表因过度预留索引而拒绝新包的问题。100 Mbps 输入超过 20 Mbps 瓶颈，本身就不可能无损；加密封装开销及两片中任一片丢失导致整包丢失，还会降低有效吞吐。此次没有实现根据网络反馈自动调整速率，固定 80 Mbps 仍无法自动适应突然降速。

## 根因与修改

原版每个 1500 字节 IP 包都预先分配 1500 个分片索引，每个索引两个机器字长整数。正常只需两个分片，却按最坏碎片数预留内存；4 MiB 预算只能容纳约 155 个未完成大包。瓶颈随机丢掉某些分片后，残片占位直至过期，连后续可完整到达的包也被拒绝。

新版：

- 分片偏移和长度改用两个 uint16；索引初始容量为 2，按需增长，实际容量计入预算。
- 常规 1500 字节包的活跃条目预算为 1700 字节；最多 1024 包、总预算 4 MiB 保持不变。预算包括每条目 192 字节开销额度，不等于进程 RSS 或 GC 堆的硬上限。
- 按进入时间维护链表，过期和压力淘汰无需扫描整张表；序号窗口只处理移出的 ID。
- 满表时淘汰最早未完成包，给新包机会；淘汰 ID 留在去重窗口，迟到片不能重新占位。单片完整包无需占用重组槽位，避免残片堵住 TCP ACK 等小包。
- 保留 1 秒创建起算硬超时、4096 ID 窗口、重叠片/总长度冲突拒绝、重复片校验与会话隔离。增加容量峰值、待重组数和压力淘汰指标。

单包重组微基准分配量从 **26192 降到 1656 B/op，减少约 93.7%**。两版均为 3 次分配。基准时间受其他本地任务影响，未据此宣称精确 CPU 加速倍数。

## 交错 A/B/C 对照

在北京服务器的独立 network namespaces 内测试。每轮按 old → compact → evict 运行，重复三轮，每次 UDP 负载 10 秒。内层 UDP payload 1472 字节，即完整 IPv4 包 1500 字节；外层 netem 20 Mbps、队列 100；固定 pacer 80 Mbps。实验不改宿主机 uplink qdisc，也不增加隧道默认路由。

| 版本 | 接收 Mbps 均值（范围） | 丢包率均值 | 重组容量拒绝/轮 | 服务端 CPU 均值 | RSS 峰值的三轮均值 |
|---|---:|---:|---:|---:|---:|
| old 原版 | 2.77（2.72–2.85） | 97.11% | 14237 | 14.02% | 15.51 MiB |
| compact 紧凑索引/改进清理/完整包快路径，关闭压力淘汰 | 11.07（11.03–11.13） | 88.70% | 0 | 14.02% | 10.82 MiB |
| evict 最终版，开启压力淘汰 | 11.00（10.94–11.06） | 88.76% | 0 | 14.45% | 11.10 MiB |

CPU 100% 表示一个逻辑核，采样包含少量准备/收尾时间；它反映此过载场景，不代表满速公网 CPU。新旧 CPU 接近，接收有效数据约四倍，RSS 更低。

新版在该工况峰值只有约 670–700 个待重组包、约 1.1 MiB 预算，**压力淘汰次数为零**。因此这里的主要增益不能归功于淘汰策略；关闭淘汰的 compact 也得到相同改善。满 1024 槽时的淘汰与新包完成能力通过定向单元测试验证。

本机 iperf3 3.9 的部分服务端 UDP JSON `end.sum.bytes` 为零，但 intervals 中有实际接收数据。本报告按服务端 intervals 接收字节/时长计算 goodput；丢包率读取其有效的最终计数。原始 JSON、日志、qdisc 和 CPU 样本保留在 `reassembly-ab/`，汇总在 `reassembly/ab-summary.json`。

## 速率匹配诊断

仅在隔离环境将 pacer 改为 18 Mbps，外层瓶颈仍为 20 Mbps、应用仍输入 100 Mbps，各跑三轮：原版约 15.87 Mbps，最终版约 15.66 Mbps。新版重组超时为零、峰值待重组仅 1–2 个。部分诊断轮次与另一隔离回归的准备阶段同机运行，因此不据小差异排名版本。

说明适当源端限速可以避免途中持续丢碎片，过载主要在全包队列处丢弃。应用提供 100 Mbps 时总丢包仍约 84%，不能将它解释为“18 Mbps 发送仍在网络丢 84%”。公网仍保持用户指定的 80 Mbps，未自动改成 18 Mbps。

后续若要适应变化的带宽，需要单独设计接收反馈和自适应 pacer。它能改善利用率与延迟，但不能创造带宽；FEC/重传也需要额外带宽和时延权衡，本轮没有添加。

- `go test -race ./...`、`go vet ./...` 通过。
- 重组输入 fuzz、带操作序列的状态 fuzz 各 10 秒通过；验证链表/map/字节计数一致、严格容量边界、重复和过期处理。
- 定向覆盖：1024 个两片大包、表满新包、完整单片旁路、1500 个一字节片、索引增长预算、超大 ID 跳跃和 uint64 边界。
- 公网两端已部署修复版，1500 字节 DF ping 通过。

公网 TCP 各方向测 15 秒（80 Mbps pacer）：北京→香港 **67.17 Mbps**，香港→北京 **66.89 Mbps**。对应北京 CPU 均值 33.12% / 30.69%，香港 52.48% / 53.41%（100%=一核）；RSS 峰值约 12–13 MiB。与前次修复前公网 67.89 / 63.09 Mbps 相比，没有明显退化，但不是同一时刻的严格公网 A/B，不能把差异全部归因于代码。原始数据在 `reassembly/public-*.json`。

网络故障回归全部通过（`reassembly-regression/scenarios.log`）。使用独立命名空间：28–1500 字节 ICMP，拒绝超过 MTU；每方向 50±15 ms 延迟、0.5% 丢包、2% 重复、15% 乱序下 TCP；20 Mbps 过载；10 秒和 90 秒断网后恢复；10000 个未认证畸形 UDP 包冲击；35 秒空闲恢复。此次未重跑此前的 120 秒混合 soak。首次回归在场景切换时因 iperf 上轮控制连接未完全退出而报 server busy；为下一场景分配独立服务端口后重跑，未把首次错误记作隧道失败或通过。

抓包观察到外层 UDP 最大 1153 字节、无外层 IP 分片、无重复应用 DTLS record 序号。两端部署二进制 SHA256 见 `binary-sha256.txt`。宿主机默认路由仍走 eth0，`dtun-exit` 仅有明确测试目标路由，表 51880 无默认路由。
